# Agent notes — HAND-OWNED, never machine-written

`scripts/gen_changed_markers.sh` overwrites `.changed_markers` on every run and
knows nothing about this file, so anything written here survives regeneration.

## Two files, two owners

| File | Owner | Contents |
| --- | --- | --- |
| `.changed_markers` (gitignored) | `scripts/gen_changed_markers.sh` | `# HEAD:` stamp, dirty count, scope summary, then the full 3-line-context diff of what is dirty right now |
| `.agent_notes.md` | you, by hand | facts that outlive a regenerated diff: unresolved causes, unverified claims, machine-local damage, the baseline sweep |

The split exists because the generator used to overwrite this prose. A state
ledger that a script can silently delete is worse than no ledger at all.

Housekeeping: when an item here is fixed, delete it or restate it as RESOLVED
with the commit that fixed it. A fixed item left lying around reads as if it
were still true, which is the exact failure this file exists to prevent.

## [2026-10-01 — "Commit Lyrics" removed: debounced auto-save replaces it]

The explicit Commit gate is GONE. The Lyrics field in the main editor is now
always editable and writes itself 400 ms after typing stops. This is the third
state this field has been in, so the reasoning is recorded rather than the diff:

1. It wrote on EVERY keystroke with no snapshot (silent, unrecoverable edit).
2. "✔ Commit Lyrics" fixed that but made the field read-only until "✏ Edit
   mode" was ticked, and text left uncommitted was discarded on the next click.

What replaced the button is not a smaller button but four guarantees, one test
group each in `tests/test_lyrics_inline_editor.py`:

- **Debounced.** `on_lyrics_edited` only re-arms `_lyrics_save_timer` (a
  single-shot `QTimer`, `dataset_manager.py`). `_flush_lyrics_edit` does the one
  write. Interval is **400 ms** — deliberately longer than the 220 ms preview
  debounce in `ui/lyrics_studio.py`, which only repaints; this one snapshots the
  undo stack and rewrites `dataset.json`.
- **Undoable**, with the OLD text in the snapshot: the snapshot is taken inside
  the flush, before the write. Taken after (or with the writer first) and Undo
  would "restore" what you just typed.
- **Backed up once per song per session** to `<dataset>/_Backup/songs/<name>.json`
  before the first change (`_backup_song_once`, guarded by `_songs_backed_up`).
  Once, not per save — re-backing-up on every save leaves you holding the state
  you just replaced, the same trap `_unique_backup_path` exists for.
- **Refuses a stale field.** `_lyrics_selected_filename` is set at load time; if
  the field no longer belongs to the selected track the pending write is dropped
  and the status label says so. This is the only way an auto-save could reach the
  wrong track.

REMOVED: `lyrics_edit_check`, `lyrics_commit_btn`, `lyrics_revert_btn`,
`_lyrics_edit_active`, `on_lyrics_commit`, `on_lyrics_edit_mode_toggled`.
`lyrics_revert_btn` became `lyrics_discard_btn` ("↺ Revert to saved") — it only
refills the field, because the auto-save has already written; undoing is Ctrl+Z.
`QTimer` had to be added to the `PySide6.QtCore` import (it was not there).

`raw_lyrics` on this path holds the PRE-edit text (not the new text), which is
what keeps the Lyrics tab's tidy pass re-runnable after an auto-save.

## [2026-10-01 — three structure-tag tidy rules, on the "Tags & checks" page]

The user asked for the tag fixes to live on the **Tags & checks** page (NOT the
Lyrics tab, where the other tidy options are) with a button for the selected
track and one for the whole loaded dataset. The rules, in
`modules/lyrics_normalizer.py`, run as block-wide passes BEFORE the per-line
loop and are each switchable:

1. `strip_quotes` — remove every `"` (straight and curly). **Order is load
   bearing:** it must run before `capitalize_first_word`, which bails on a line
   that starts with punctuation (`:270`), so a later strip would leave `"hello`
   lowercase. `_QUOTE_CHARS` also bites curly variants.
2. `trim_tag_modifiers` — `inner.partition(" -")[0]` when `" -"` is present.
   `[Chorus - Raspy Vocals]` -> `[Chorus]`; a JOINED hyphen is not a separator,
   so `[Pre-Chorus]` is untouched. **Language exempt:** a head matching
   `^[A-Z]{2}$` is returned verbatim, because `docs/section_markers.txt:45-47`
   and `docs/descriptor_reference.md:390,410` define `[EN - Verse]`,
   `[EN - Chorus - anthemic]`, `[JA - Verse - whispered, sparse]` — literal
   trimming would delete the language declaration.
3. `drop_stray_tags` — consecutive tag-only lines: keep the first, drop the rest.
   The requested example `[Verse 1]\n[Raspy Vocal] [Mid-Tempo Groove]` -> `
   [Verse 1]`. A tag after lyric text, or after a blank line, is NEVER dropped,
   so the legal shape from docs/ACE_Step_1.5_Master_Annotation_Guide.md:51
   (one tag per section, sections separated by `\n\n`) survives.

`---- filename ----` markers are split out and re-inserted around the tag passes
so no tag rule can reach into a separator and break all-lyrics write-back.

Sub-decisions worth not re-litigating:
- **Report counters count ELEMENTS, not characters.** `tags_trimmed` compares
  the bracket lists before/after and counts those whose text changed — a
  `findall()` length difference is always 0 for a trim, which is how it was
  first written (and caught by a test).
- **`_tidy_one` is pure**; `_apply_tidy_to` does the writing, with
  `_backup_song_once` called BETWEEN them. Mutating in the first function made
  the backup capture the already-tidied text.
- **Per-song `.txt` is `<stem>_lyrics.txt`, never `<stem>.txt`.**
  `modules/exporters.py:export_sidecar_captions` already owns `<stem>.txt` for
  the caption; a bare name here would be silently overwritten on the next export.
  Tested with the caption file pre-created and asserted unchanged.
- **No linter added.** None is installed and none is anticipated; verification is
  `python -m compileall -q` on the touched files plus pytest.

## [HARNESS] -- this machine's VS Code terminal (recorded 2026-09-24)

Not a repo bug, but it masquerades as one, and it is what "the agent froze"
meant here. The terminal's shell-integration OUTPUT CAPTURE is broken: commands
run, their output shows up in the raw terminal dump, and the tool still reports
"completion could not be observed" and exits 1. What that does to long commands:

- A NON-DETACHED command is killed when the next command arrives ("starting
  another foreground command will attempt to close it"). A job backgrounded
  with a plain `&` dies with it, and a redirected python buffers its stdout, so
  the kill leaves an EMPTY LOG. An empty log therefore means "killed", not
  "failed" -- the tail of the 2026-09-21 session and the first suite run here
  both ended exactly that way.
- MEASURED: a full-suite run reached `[100%]` and then vanished with no summary
  line (`ps -p <pid>` afterwards printed only a header). The same suite launched
  with setsid wrote `EXIT=0` and finished normally.
- `DatasetManager()` is not hung but is slow ONCE per process: ~30-60 s, nearly
  all of it Qt's FFmpeg multimedia plugin init. A boot check read at 45 s looks
  hung and is not -- wait for the first line before concluding anything.

THE RECIPE that works here:

    setsid nohup bash -c 'CMD > /tmp/out.log 2>&1; echo EXIT=$? >> /tmp/out.log' \
      < /dev/null > /dev/null 2>&1 & disown

then poll `/tmp/out.log` with a FILE READ rather than with another command, and
use `python -u` for anything that prints. setsid moves the job into its own
session, so it survives the terminal being closed under it.

- `pytest.ini` already passes `addopts = -q`, so adding `-q` again makes it
  `-qq`, which SUPPRESSES the trailing "N passed" line -- a green run then looks
  like bare dots with no summary. `EXIT=0` is the real signal; for a count use
  `--collect-only -q -o addopts=`.
- MEASURED 2026-09-27, so a later reader does not think the tests hang: a
  module whose fixture builds a real `DatasetManager` costs ~80 s PER TEST when
  the fixture is function-scoped (a 20-test file hit the 1200 s timeout at
  15 tests) and ~16 s TOTAL when it is module-scoped
  (`tests/test_track_table_columns.py` re-run after the fix: 22 tests on one
  module-scoped window, as in `tests/test_lyrics_inline_editor.py`, in 15.84 s).
  Copy that pattern and reset state in a `_load()` helper instead of paying for
  a new window per test. An empty redirect file still means "the terminal killed
  it", never "it failed".

## [2026-09-27 — text size: one global base, one lyrics override]

`.agent_notes.md` entry for the font-size follow-up to the lyric-tooling pass.
Two layers, deliberately different knobs:

- ``ui_font_size`` — the base size every widget inherits, consumed by
  ``build_stylesheet(font_size=...)``. ``0`` = Auto = ``DEFAULT_FONT_SIZE`` (13),
  which is what the hard-coded ``13`` in ``build_stylesheet`` used to be, so the
  default look is byte-identical with no setting present.
- ``lyrics_font_size`` — an override for the lyrics surfaces only. ``0`` = Auto =
  inherit the base, which is implemented as "emit NO rule", because a rule pinned
  to the base would stop tracking the base the moment it changed.

DECISIONS THAT ARE EASY TO REVERSE BY MISTAKE:

- **The override is a stylesheet rule, NOT ``QWidget.setFont``.** MEASURED, and
  it invalidates the obvious implementation: the app stylesheet's
  ``* { font-size: Npx }`` overrides a widget's own font the next time the theme
  is applied, so a field with ``setFont(pixelSize=26)`` snapped back to the base
  on the very next theme switch / zoom change / global-size change. A dynamic
  property rule (``[fontRegion="lyrics"] { font-size: Npx }``) outranks ``*`` and
  survived re-apply and ``repolish`` in the same probe. Hence
  ``FONT_REGION_PROPERTY`` in ``ui/themes.py``.
- **Corollary: ``LyricTextEdit.__init__``'s ``setFont(Consolas, 13pt)`` has been
  dead in the app since the ``*`` rule existed** — polished, it reports the QSS
  px size (13px/lineH 18, not 13pt/lineH 23). It still matters for the
  pre-stylesheet moment (and the family still wins, which is what picked
  Consolas). Do not "fix" the pt/px mismatch: changing it shifts the default
  text size for every lyrics surface at once.
- **Two controls, ONE setting, cross-synced** (``sync_font_size_controls``). The
  inline one sits on the field's ACTIONS row, not its header, so it survives
  "Expand" (the header is fine too, but the actions row is the strip that stays
  visible) and because the header already carries three checkboxes.
- **``ui_zoom`` is scaled into BOTH sizes.** Zoom magnifies the whole look; if it
  scaled only the base, a lyrics override would eventually be overtaken by the
  base at higher zoom and the setting would appear to invert.
- **``_set`` was renamed ``set_appearance``** because ``dataset_manager`` now
  calls it from the inline control's handler; a cross-module import of a
  private name is how the next reader concludes it is internal.
- **Coverage note:** ``tests/test_lyrics_inline_editor.py`` gained an autouse
  ``_settings_sandbox`` fixture. That file's module-scoped manager RESTORES
  ``SETTINGS_PATH`` right after construction, so without the fixture a size test
  would write the developer's real settings.json. Any future appearance test in
  that file needs the same guard.

## [2026-09-28 — the capitalizer's double-click was position-blind]

Reported symptom: "a word whose last character is special (``dog.`` ``dog,``
``dog-`` ``dog"`` ``dog?`` ``dog!``) is not recognized by the double-click or the
Tab tap-along." Root cause is one Qt behaviour plus one wrong question:

- ``QTextCursor.WordUnderCursor`` answers "the word this position is IN", and Qt
  treats a trailing ``-``/``.``/``,``/``"``/``?``/``!`` as a word of its own. A
  real double-click leaves the cursor position one PAST the word, so the old
  ``toggle_word_at_cursor`` re-selected ``'.'`` and ``'.'.upper() == '.'`` — a
  silent no-op. Measured at position 3 of ``dog.``: selection ``'.'``.
- **The old code threw away the answer it had been handed.** ``mouseDoubleClickEvent``
  calls ``super()`` first, so Qt had ALREADY selected ``dog`` correctly; the
  gesture then re-derived the word from the position and lost it. This is why the
  bug read as "the word is invisible" rather than "the selection is wrong".
- **``dog dog`` worked, which is why the bug hid.** At ``word + 1`` on a space,
  ``WordUnderCursor`` returns the PRECEDING word, so the gesture accidentally
  succeeded. Every case in the report is trailing punctuation; the pre-existing
  test set the text programmatically and called the gesture with a position
  INSIDE the word, so it passed even while the real path was broken.
- **Fix:** ``_word_under_or_before()`` probes ``position`` then ``position - 1``
  and accepts the first selection containing an alphanumeric; the selection Qt
  already made wins when there is one. This is position-independent, so clicking
  any letter of the word works.

HONEST SCOPE OF THE TAP-ALONG CLAIM, because the plan asserted more than held:

- **The punctuation half of the tap-along bug did NOT exist.** Measured against
  the old code: ``capitalize_and_advance`` on ``dog. dog, dog- dog" dog? dog!``
  already produced ``DOG. DOG, DOG- DOG" DOG? DOG!`` in 6 presses, because
  ``NextWord`` skips a punctuation character on its own. Only the double-click
  was broken there.
- **The apostrophe half was real and hit both gestures.** Qt splits ``don't``
  into THREE words (``don``, ``'``, ``t``) and ``o'clock`` into two, and
  ``NextWord`` stops on the leftover ``t``. Measured on ``don't stop believin'``:
  the walk visits 3, 4, 6, 11, 19, 20 — so 4 presses capitalized what a singer
  sings as 3 words, and a double-click on ``don`` uppercased only ``DON't``.
  ``_join_apostrophes()`` widens a word across an apostrophe **only when there is
  an alphanumeric on BOTH sides**, which is what keeps a trailing ``believin'``
  and a quoted ``'n'`` out of the word.
- **The contraction stop is JOINED, not skipped** (skip only if its Qt selection
  is exactly ``'`` or ``’``). Skipping the ``t`` would jump the cursor to
  ``stop`` and leave ``DON'stop`` whenever the cursor started mid-contraction —
  e.g. a ``toggle_case``-style hand-placed cursor, or a click on the left half of
  the word. ``test_the_contraction_tail_is_joined_not_merely_skipped`` guards it.

DELIBERATE, and pinned by a test rather than left implicit: a double-click
EXACTLY on the punctuation is still a no-op (Qt hands over the mark alone and
uppercasing it changes nothing). Reaching BACKWARDS to the word before the mark
was offered and declined — clicking the word's own letters is the gesture.

Verified: 44 capitalizer tests, 75 with ``test_lyrics_inline_editor.py``, 100 with
the neighbours, all EXIT=0. **Proven to discriminate**: the 17 new cases were run
against the OLD bodies (monkey-patched in a throwaway script) — 15 fail, and the

## Guardrails against silent dataset loss + the Appearance freeze

Two separate failures, one underlying cause: the dataset JSON was treated as if
only one thing could ever write it, with no safety net when that was not true.

- **The "lost hour" was the DELETE path, not the capitalizer.**
  `_remove_sample_at` backed up the *audio* and then `samples.pop(idx)`. The
  caption/lyrics lived ONLY in the sample list, so the next `save_dataset` wrote
  the dataset without them. The backup chain confirms it: 052254/052618 held 34
  samples, 163239 and the live file held 33 (`Cold_Hearted_Man` gone). The audio
  was never the thing lost. FIX: `_backup_sample_json` writes the dropped
  sample's JSON (caption, lyrics, every field) to `<dataset>/_Backup/deleted/`
  (falling back to `project_backups/deleted/` when no dataset is open) BEFORE the
  pop, whatever the audio's state — a track whose file was missing (never
  rendered, detached drive) used to be deleted with NOTHING preserved.

- **Save is atomic and its backup can no longer be lost.** `save_dataset` takes
  the pre-save copy through `_backup_file`, whose name now gains a `-1`, `-2` …
  suffix on a same-second collision (the old second-resolution `.bak-<stamp>`
  silently overwrote the older backup with `shutil.copy2`). It then writes
  `<path>.tmp` and `os.replace()`s it over the target, so a crash or a
  non-serializable value leaves the COMPLETE old file instead of the zero-byte
  one the old `open(path, "w")` truncated to first. If the pre-save backup cannot
  be taken, the save ABORTS and writes nothing.

- **A second instance is refused** (`main.py`). Two windows were two writers on
  one file; the save path can make a single write atomic but cannot merge two
  whole copies, so the last save silently won. `QLocalServer` + `QLockFile` under
  `QStandardPaths.RuntimeLocation`; a second launch raises the first and exits.
  `QLockFile.setStaleLockTime(0)` so a crash cannot wedge every later launch (the
  30 s default would).

- **The ~7 s Appearance/zoom freeze was `setStyleSheet` on the QApplication**
  (measured: app-wide 5.9 s vs window-scoped 1.08 s per step; `setPalette`
  0.001 s — it was re-polish, never resize). `apply_custom_theme(scoped=True)`
  now sets the sheet on the WINDOW (`ui.themes.apply_theme_to`) for live changes;
  startup keeps the app-wide `apply_theme` so the first paint styles dialogs too.
  Dialogs and the Lyrics Studio are Qt children of the window and inherit the
  scoped sheet; only the palette stays app-wide (tooltips).

Tests added: `test_track_delete.py` (metadata backup, no-audio track, same-second
backup names, abort-on-failed-backup) and `test_themes.py` (scoped vs app-wide);
`test_single_instance.py` is new. Verified offscreen end-to-end with
`/tmp/smoke_guard.py` and the suite; the key repeat-rate feel still needs a real
display to sign off.
